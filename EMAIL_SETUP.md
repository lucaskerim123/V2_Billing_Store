# OrbitFS Mail configuration

OrbitFS has its own Mail system. Mailboxes, sender identities, reply routing, templates, automations, delivery history, spam rules and lifecycle configuration are owned by OrbitFS and stored in Supabase.

Resend is the transport provider only. It is used to deliver outbound messages and, where enabled, expose received-mail data to OrbitFS Mail.

## Customer-facing Store URL

The current public Store/Billing origin is `https://orbitfsstore.vercel.app`.

OrbitFS stores the canonical address in Supabase as `site.public_url`. Customer-facing links generated by Mail-backed flows, including password reset, email verification and guest support, resolve through that canonical Store origin.

`NEXT_PUBLIC_ORBITFS_STORE_URL` may be used as an intentional deployment override. The older `NEXT_PUBLIC_SITE_URL` is accepted as a compatibility fallback, but normal Store URL changes should be reflected in `site.public_url`.

## Vercel environment variables

Set these on the V2_Billing_Store Vercel project for **Production, Preview and Development** as appropriate:

### Required for outbound mail

- `RESEND_API_KEY` — your private Resend API key. This is the primary OrbitFS Mail outbound transport key and is required for registration confirmation, password-reset mail, transactional mail, manual mail and the Mail test endpoint.

### Optional separate inbound/mailbox key

- `RESEND_MAIL_API_KEY` — optional private Resend API key used for mailbox/receiving operations. If this is not set, OrbitFS Mail now falls back to `RESEND_API_KEY`, so a second key is not required for the normal setup.

### Supabase infrastructure

- `NEXT_PUBLIC_SUPABASE_URL` — the Store Supabase project URL.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — the Store Supabase publishable/anon key.
- `SUPABASE_SERVICE_ROLE_KEY` — server-only Supabase service-role key where Store server workflows require it. Never expose this to browser code.

### Optional Store origin override

- `NEXT_PUBLIC_ORBITFS_STORE_URL` — normally `https://orbitfsstore.vercel.app` only when an explicit deployment override is required.

Do **not** put normal OrbitFS Mail configuration in environment variables.

The following legacy Mail variables are retired and can be removed from Vercel after the runtime-config version is live:

- `EMAIL_FROM`
- `EMAIL_REPLY_TO`
- `EMAIL_SUPPORT_FROM`
- `EMAIL_BILLING_FROM`
- `EMAIL_ADMIN_FROM`

Their values now come from OrbitFS Mail settings, mailbox accounts and template sender accounts in Supabase.

## OrbitFS Mail settings

Manage these inside OrbitFS Mail:

- Default sender display name
- Default outbound sender address
- Default Reply-To address
- Customer-message sender address and display name
- Admin, Billing, Support and other mailbox identities
- Inbound mail domain and enable/disable state
- Mailbox display names and access
- Templates and template sender accounts
- Lifecycle automations
- Delivery history
- Spam protection

The live runtime configuration is stored in `mail_settings`. Mailbox-specific display identities are stored in `mail_accounts`.

## Delivery architecture

1. OrbitFS decides which mailbox/template/automation should send the message.
2. OrbitFS creates the delivery/outbox record and reference ID in Supabase.
3. OrbitFS resolves sender identity and Reply-To from Mail configuration.
4. Customer-facing links resolve against the canonical OrbitFS Store address.
5. Resend receives the finished message only as the delivery transport.
6. OrbitFS records success/failure and provider message IDs back into its own Mail history.

The mailbox reader uses `RESEND_MAIL_API_KEY` when present and otherwise uses `RESEND_API_KEY`. This prevents the Mail system from failing simply because a second Resend key was not configured.

## Security

Never commit API keys, service-role keys or provider credentials to GitHub. Non-secret sender addresses and Mail behaviour belong in Supabase configuration, not Vercel secrets. The private payment-webhook sync token is generated/stored in Supabase and is never public-readable.
